# Боевой рублёвый кошелёк: техническая подготовка 07.11.2026

**Статус на 08.11.2026: весь исходный код находится в `main`; новый платёжный модуль НЕ опубликован на REG.RU и НЕ подключён к публичному API. Боевая оплата отключена.**

## Что сделано

- Новый закрытый PHP-модуль: `account-service/private/wallet-real.php`.
- Подготовлен второй закрытый модуль: `account-service/private/wallet-real-payment.php`: создание платежа по API для `bank_card` или `sbp`, фиксированный адрес возврата на действующий домен, 64-символьный стабильный Idempotence-Key, повтор без двойного запроса, проверка ответа ЮKassa, сохранение payment_id и ссылки подтверждения. Публичного маршрута пока нет.
- Боевой ключ ShopID 1515851 уже безопасно установлен на REG.RU через GitHub Actions, при этом параметры реальных платежей остаются выключенными.
- Отдельные таблицы для реальных денег: numi_real_wallet_balances, numi_real_wallet_topups, numi_real_wallet_spends, numi_real_wallet_ledger, numi_real_wallet_merges, numi_real_wallet_fiscal_events и numi_real_wallet_refund_cases.
- Существующие numi_wallet_* — только TEST. Тестовые остатки 100/200 ₽ нельзя переносить в реальные. Они остаются без изменений; реальные балансы всегда начинаются с нуля.
- Для боевых прав на ответ и скидки клуба сервер читает только подтверждённые покупки с provider=real_wallet. Тестовые покупки и подписки никогда не дают скидку в боевой системе.
- Списания и начисления в целых копейках, одна транзакция на сумму + операцию + оплаченный материал + запись в истории. Запрос с тем же idempotency key не списывает повторно.
- Привязка намерения пополнить баланс; сверка только через серверный GET к live ЮKassa и проверка суммы, RUB, магазина, metadata, статуса, тестового флага и чека.
- Новая реализация создания платежа требует уже подготовленных и проверенных **сервером** фискальных реквизитов; не придумывает признак аванса, налоговую ставку и не принимает чек из браузера. При отсутствии реквизитов платёж не создаётся.
- Даже если платёж завершён, без подтверждённого чека зачисления пока нет. Дублирующее подтверждение ничего не начисляет.
- При внешнем возврате уже зачисленного пополнения система замораживает реальные операции до ручной сверки, не рисует отрицательный баланс.
- При покупке создаётся запись в фискальном журнале об обязательном чеке зачёта аванса. Отправка пока заблокирована до настройки кассы.
- Подписки в новом режиме продлеваются вручную, без автоматического списания с карты.
- Для создания реального пополнения и покупки пока требуется подтверждённая почта клиента — контакт для чека; Telegram-only без неё будет просить подтвердить контакт.
- Создана отдельная проверка на MySQL 8.0. Новые файлы не меняют действующий сайт, бота или API.

## Технический переключатель

Новый модуль вообще НЕ подключён к публичным обработчикам. Для будущей активации дополнительно требуется строгое совпадение всех условий приватной конфигурации:

- wallet_mode = live, real_wallet_enabled = true
- fiscalization_verified = true
- refunds_verified = true
- advance_offset_receipts_verified = true
- offset_receipt_worker_verified = true
- launch_approved = true, provider_test_mode = false
- цифровой shop_id и секрет с префиксом live_

Все выключено по умолчанию; ключи не хранятся в GitHub. Фактическая работа ЮKassa не включается одной заменой test_ на live_.

## Что обязательно закончить после подключения кассы

1. Согласовать с конкретной кассой способ оформления чека на аванс при пополнении и отдельного чека зачёта предоплаты при выдаче ответа/подписки. Не угадывать налог, признак предмета расчёта и способ расчёта.
2. Создание платежа `POST /payments` **написано в закрытом модуле**, для карты и СБП; проверено на макетах ответов API в CI. Осталось согласовать кассовую схему и подключить **серверный** генератор корректного чека. Не открывать публичный маршрут и не включать real-wallet flags до этого.
3. Реализовать и проверить обработчик фискальных событий advance_offset, повторы, ошибки, повторный вход и сбой отправки чека; пока outbox только сохраняется.
4. Реализовать операторский полный/частичный возврат с правильными чеками и анализом уже израсходованного аванса; прямое выполнение возвратов пока намеренно запрещено.
5. Подключить перенос реальных остатков при связывании Telegram/email к общей транзакции объединения аккаунтов. Функция подготовлена, но ещё НЕ вызвана действующим core.php.
6. Согласованно переключить API и проверку доступов к материалам и клубу на реальный режим; сегодня у действующего API права по-прежнему учитывают тестовые покупки.
7. Сохранить резервные копии и контрольные суммы действующих файлов REG.RU, отдельно проверить SQL, фискальные события, повторные операции и два независимых аккаунта.
8. Выполнить минимальную реальную покупку с фактическим чеком, выдачей ответа и проверкой возврата перед приёмом денег клиентов.

## Что именно уже проверяет автоматический тест

- Жёсткое разделение TEST и REAL по счетам, операциям, покупкам, клубу.
- Нельзя активировать реальный режим с тестовым ключом или без проверки чеков и возвратов.
- Неактивный email/отсутствующий фискальный контакт не допускает реального пополнения.
- Ошибочная сумма, валюта, магазин, metadata, тестовый платёж отклоняются.
- Платёж без зарегистрированного чека не зачисляется; повторное уведомление не начисляет дважды.
- Покупка и повтор той же покупки с одним ключом не дают двойного списания.
- Цена 20 ₽ без реального клуба и 10 ₽ с ним; истечение подписки.
- Учёт чеков аванса и зачёта, сверка ledger=balance, блокировка при внешнем возврате.
- Проверка объединения аккаунтов; активный ожидающий платёж не даёт объединять деньги.
