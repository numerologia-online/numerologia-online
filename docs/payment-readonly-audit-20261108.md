## Критические задачи до настоящей продажи

### P0 — блокируют запуск

1. **Чеки за аванс и зачёт.** Текущие «Чеки от ЮKassa» могут не поддерживать произвольный аванс для пополняемого баланса. Нужен письменный ответ провайдера по точному сценарию и законный фискальный обработчик. Не включать реальные пополнения раньше этого.
2. **Боевой POST /payments отсутствует.** `naRealWalletTopupIntent()` записывает намерение; код создания платежа с фискальными реквизитами и сохранением `provider_payment_id` в реальной ЮKassa пока не реализован. Нет боевой webhook/reconciliation очереди.
3. **Нет фискального обработчика зачётов.** Таблица `numi_real_wallet_fiscal_events` фиксирует ожидающий чек `advance_offset`, но реальная отправка, проверка статуса и безопасные повторные попытки отсутствуют.
4. **Возвраты пока намеренно заблокированы.** В `naRealWalletRefund()` исключение; требуется полный и частичный возврат с фискальной и бухгалтерской сверкой, особенно когда часть аванса уже потрачена.
5. **Доступы и показы не переключены.** `naCatalogHasAccess()`, `naMaterialServe()`, `naPurchases()` и `naSubscriptionList()` читают общие entitlements без фильтра `provider`. Во время боевого запуска потребуется единый переключатель для статуса клуба, выдачи ответов, истории и подписок, чтобы sandbox не открывал реальные покупки.
6. **Фронтенд ещё test-only.** `wallet-client.js` и `account-browser.js` требуют в ответе `test:true`, используют тестовые подсказки; серверная смена без согласованной замены UI нарушит покупки.
7. **Telegram/email merge.** Подготовленный `naRealWalletMergeAccounts()` ещё не вызван в `core.php`; при запуске надо атомарно переносить реальный баланс и операции вместе с аккаунтом. Должны быть отдельно протестированы слияния с pending/credited пополнением и одинаковыми request keys.
8. **Контакт для чека.** Новый модуль не допускает оплату без верифицированного email; Telegram-only пользователю нужен согласованный ввод/верификация email либо телефона перед пополнением.
9. **Нет проверенного боевого полного цикла.** Нужна реальная контрольная оплата с чеком, проведение 20→10 ₽ по реальной подписке, выдача ответа на месте, возвраты, повторный вход, синхронизация платежей после сбоя и двух параллельных нажатий.

### P1 — улучшения и контроль

- Серверная сверка `SUM(ledger.delta_kopeks) = balances.kopeks` для каждого реального аккаунта и ежедневная сверка с платежами ЮKassa. Мониторинг необработанных платежей/чеков/возвратов.
- Протокол/восстановление после обрыва запроса POST /payments. ЮKassa гарантирует idempotency только в течение 24 часов; после этого без GET-сверки нельзя послать новый POST.
- Отдельный владельческий доступ для фискальных ошибок; не показывать секреты или email покупателя в публичных логах.
- Тесты реальной конкурентной покупки, edge cases блокировок и staging-проверка полного пути клиента на реальном REG.RU.

## СБП — обязательный способ оплаты вместе с банковской картой

СБП = Система быстрых платежей. **Добавить как способ пополнения существующего баланса, НЕ как отдельный баланс.**

- ЮKassa API: `payment_method_data.type="sbp"`, `confirmation.type="redirect"`, `capture=true`; `return_url` должен вести на наш подтверждённый сайт. На компьютере QR-код, на телефоне переход в банк.
- Для карты и СБП один серверный сценарий: `topup intent` → live ЮKassa → GET `/payments/{id}` → фискальный чек → атомарное зачисление. Логика списания за вопросы/подписки не зависит от платёжного метода.
- В интерфейсе пополнения предоставить простой выбор **«Картой» / «СБП»**, если оба доступны настоящему магазину. Не возвращать корзину.
- Не включать сохранённый платёжный метод для СБП автоматически. Наши подписки пока продлеваются вручную из баланса; отдельное согласие понадобится, если позже добавим автопродление.
- Убедиться, что при возврате СБП транзакции правильно привязаны к возврату ЮKassa и фискальным операциям.
- СБП должна быть включена у боевого магазина shop_id `1515851`; API поддерживает метод, но **её фактическая доступность для этого магазина ещё не проверена**.

Официальная документация: https://yookassa.ru/developers/payment-acceptance/integration-scenarios/manual-integration/other/sbp
