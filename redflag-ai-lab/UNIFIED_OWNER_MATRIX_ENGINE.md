# Единый редакторский движок «Мужчина / Red Flag»

**Статус:** подготовлено и проверено в GitHub `main`. **Не опубликовано на REG.RU.**
Это редакторское тестирование владельца, не платный пользовательский API.

## Одна схема для всех блоков

1. Сайт принимает полную дату `DD.MM.YYYY` и идентификаторы категории/вопроса, проверяя владельца и источник запроса.
2. `rfOwner31(day, month, year)` рассчитывает позиции Матрицы судьбы по действующим правилам 22 энергий (согласовано с `numerology-core.js`).
3. **Для каждого вопроса строго пять различных позиций:** `left` (день), `top` (месяц), `right` (год), затем **две позиции по смыслу вопроса** из `pointDescriptions`.
4. Позиции указаны как метаданные `matrix_points` самого вопроса в `redflag-ai-lab/catalog.json`. Нет отдельного PHP-алгоритма или промпта на каждый вопрос.
5. Значения каждой из пяти точек берутся из **одной** `redflag-ai-lab/intimacy-knowledge-v1.json`: `core`, `plus`, `minus`, `love`. Цифры/имена арканов модели не передаются.
6. Используется **ровно утверждённый текст промпта «Красных флагов»** из `rfOwnerUnifiedAnswer()` в `style-test-api.php`. Для других блоков заменяется только буквальное название раздела внутри вступительной фразы, не стиль, ограничения, структура ответа и не указания отвечать на один вопрос.
7. Модель редакторского теста: `google/gemini-3-flash-preview`; около двух абзацев, первый сразу по существу вопроса, второй — связанная подводка к другому вопросу каталога. Нельзя перечислять пять энергий как портрет.
8. Внешний вызов делается **только при ручном редакторском запросе**. Тесты GitHub Actions используют заглушку и не тратят деньги.

## Как подключать следующие десять и более блоков

Для нового блока в `catalog.json` добавить объект `{ "id", "title", "questions" }`. Для каждого вопроса указать `id`, `title` и `matrix_points` с пятью позициями. Первые три всегда `["left","top","right"]`; две последние выбираются по нумерологическому смыслу вопроса, из существующих описанных точек. Пример:

```json
{
  "id": "new-topic-question",
  "title": "Название вопроса",
  "matrix_points": ["left", "top", "right", "loveHeart", "tailFirst"]
}
```

**Не копировать пример вслепую**: дополнительные позиции должны соответствовать конкретному смыслу вопроса. В новом блоке не нужны новые PHP-функции, отдельные промпты или дополнительные копии базы. Если понадобится новая позиция из полной матрицы, сначала проверить её математический смысл и добавить человеческое описание в `pointDescriptions`, не изменяя сами формулы.

При появлении в блоке единственного вопроса подводка может указывать на вопрос из других блоков; это лучше, чем случайно придумывать название или блокировать расчёт.

## Защита работающего сайта

- **Не менялись:** шаблон идеального промпта, формулы расчётов, модель, ключи и конфигурация провайдера, оплата, авторизация, покупательские маршруты, база «Полного разбора» и «Разбора года».
- Старые раздело-специфические функции сохранены как неиспользуемый код для безопасного отката; **в активном редакторском маршруте используется только `rfOwnerUnifiedAnswer()`**.
- Текущая расширенная база 22 энергий находится в GitHub. Отсутствие публикации означает, что живой REG.RU пока читает старые данные.
- Любой будущий перенос на REG.RU проводить отдельной контролируемой публикацией PHP + каталога + общей базы после сверки текущего состояния сервера и резервного копирования. Нельзя автоматически затирать отличающиеся живые файлы.
- Offline QA: `.github/workflows/numi-owner-unified-offline-qa.yml`, `366 × 56 = 20 496` сценариев, платных вызовов `0`.

## Важно о смысле трактовок

Плюс и минус в Матрице судьбы описывают символические варианты проявления; реальные измены, агрессию, принуждение или финансовую надёжность невозможно установить по дате рождения как факт. Вывод должен отражать относящуюся к вопросу конкретную тему, а не безусловное обвинение и не полный психологический портрет.
